PVS shift automation + daily report, added 2026-07-27. See [[sony-smt-parts-verification]] and [[pvs-model-naming]].

**Shift schedule is now config-driven and testable.** `Pvs.Core.Shifts.ShiftSchedule` gained `ShiftKey(DateTime)` — a stable per-shift-period id ("2026-07-27|Night"), where a Night span before midnight and after midnight share the SAME key (dated to the shift's start day). `SessionCoordinator` delegates `CurrentShift`/`CurrentShiftKey`/`ShiftKey()` to `config.ToShiftSchedule()` (no more hardcoded 07:30/19:30 in the coordinator). Tests in `ShiftScheduleTests.cs`.

**Four shift features the user asked for ("all of 1-4") + the 7:35 trigger, all deployed:**
1. **Current shift on the monitor** — `/api/status` `verify.currentShift`/`currentShiftKey`; monitor header shows "· Day/Night shift".
2. **Auto-trigger shift-change check at 07:35 / 19:35** — `SessionCoordinator.CheckShiftTrigger()` runs off the 30s housekeeping timer. REWORKED 2026-07-28 to be smart about the morning changeover (it was colliding with the lot-start model check): now uses a **60-min grace window** from 07:35/19:35 (not one instant) and a `_shiftTriggerDone` HashSet of shift keys. Within the window it: (a) marks satisfied + skips if a ModelChange/LotEnd/ShiftChange already COMPLETED this shift (`CompletedThisShift` via each completion's ShiftKey) — a fuller check counts; (b) waits/retries if a check is in progress (never interrupts); (c) else starts `StartFullScan(ShiftChange)`, waiting at AwaitingBadge. 07:35/19:35 still HARD-CODED (shift start +5 min).
3. **Per-shift reset of the status buttons** — each `VerifyCompletion` now carries `ShiftKey`; the monitor shows a check GREEN only if `comp.shiftKey === currentShiftKey`, so last shift's pass greys out to "not done this shift".
4. **Forecast already honours the schedule** — `/api/forecast` uses `ToShiftSchedule()` + `running` predicate with `nightRunning=false` (day-mostly), so exhaust wall-clock skips idle night hours. No change needed.

**Line-downtime tracking (new).** `Pvs.Core.Runtime.DowntimeLog` (pure, tested) records line up/down spans from samples of "any machine online"; excludes pre-shift boot idle via `FirstUp`; open span counts to now. `Pvs.LineApp.Runtime.DowntimeService` samples every 30s, persists to `C:\PvsLineApp\downtime.json` keyed by date (survives PVS restart, resets at day boundary), exposed via `LineService.Downtime`.

**Daily report** — `GET /api/report/daily?date=yyyy-MM-dd` (default today) + `wwwroot/report.html` (linked "Daily report" from the monitor header; has a date picker + Print button, print CSS expands all machine tabs). Sections: model runs, qty produced (+excess), line downtime (spans+total), and **feeder usage by machine = expected placements = boards produced × per-board (ProductBOM.Quantity)**. Verified live: Line 1 on 2026-07-27 ran L307/B, 20 boards, 0 downtime; e.g. M2·F113 VW5-6454-104 @19/board → 380 expected.
